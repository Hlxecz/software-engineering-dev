# 발표 설명과 시연

현재 기준: **0.11.1-java.1 Windows**. [최신 설계](windows-v0.11.1/README.md)와 [실행](RUN.md)을 먼저 확인합니다.

## 1분 설명

“이 프로젝트는 사진과 메모로 글을 작성하고 티스토리에 발행하는 데스크톱 앱입니다. 기존 JavaScript 화면과 Electron·AI 연결을 재사용하고, 사용자 글·사진·초안·카테고리·프롬프트와 새 기능의 보관 자료를 Java로 옮겼습니다. Node가 JSON으로 Java를 실행하며 Java는 자료 경로와 저장 조건을 검사합니다.”

“클래스 수를 늘리기보다 책임이 다른 저장 기능만 나눴습니다. 현재 클래스 17개와 인터페이스 2개입니다. 새 원문·다듬기·수정 시도 저장을 분리하고, 실제 실패 검사가 필요한 두 저장 계약만 주입합니다.”

## 시연 순서

1. 다크/라이트 테마를 전환하고 사진 없이 직접 작성합니다.
2. 제목·본문을 보관하고 다시 열어 Java 파일 저장을 설명합니다.
3. `Main → RequestDispatcher → DraftRepository → JsonFiles`를 따라갑니다.
4. 자동 검사의 모의 AI로 선택 칸 다듬기·되돌리기 결과를 보여 줍니다.
5. 기존 글 가져오기·원문 충돌·수정 결과 미확인 흐름을 [활동도](windows-v0.11.1/FLOWS.md)로 설명합니다.

발표 중 실제 공개 발행이나 기존 글 저장은 하지 않아도 됩니다. [검증 기록](windows-v0.11.1/VERIFICATION.md)에 모의 검사와 실제 실행 범위를 구분했습니다.

## 예상 질문

| 질문 | 답변 핵심 |
|---|---|
| Java로 바꾸면 더 빨라지나요? | 언어 추가 자체가 성능 향상을 보장하지 않습니다. 이번 목적은 책임 분리와 Java 활용이며 요청별 JVM 시작 비용이 있습니다. |
| Java와 Node가 둘 다 서버인가요? | HTTP 서버는 Node입니다. Java는 요청별 JSON을 처리하는 파일 관리 프로세스입니다. |
| SOLID를 전부 적용했나요? | 책임 분리와 실제 저장 계약 주입을 적용했습니다. 모든 클래스의 인터페이스화·완전한 OCP는 하지 않았습니다. |
| 왜 되돌리기 전에 digest를 보나요? | 다른 편집 내용을 덮어쓰지 않기 위해 현재 글이 기대한 버전인지 확인합니다. |
| 실패 시 모든 장애를 복구하나요? | 지정 파일의 요청 중 실패를 복원합니다. 강제 종료·전원 장애를 DB처럼 복구하는 구조는 아닙니다. |
| 사용자 자료는 어디에 있나요? | Java 전용 workspace입니다. 원본 앱 자료와 Git·EXE에서 분리합니다. |

과제 1 PDF의 제출일과 11개 클래스는 당시 기준입니다. 현재 발표에서는 최신 설계의 19개 선언을 사용합니다.
