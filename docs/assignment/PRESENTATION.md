# 발표 설명과 시연

## 처음 30초

“이 프로젝트는 개발 화면 캡처와 메모로 블로그 글을 작성하는 앱입니다. 원본 v0.7.4의 화면과 AI·티스토리 기능을 유지하면서, 게시글·초안·카테고리·프롬프트 관리를 Java로 옮겼습니다. Java가 실제 앱의 저장 요청을 처리하며, 직접 작성한 클래스는 11개입니다.”

## 구조 설명: 약 1분

최상위 README의 폴더 트리를 보여줍니다.

- `web`: 사용자가 보는 화면
- `desktop`, `scripts`: Electron 앱, AI, 티스토리 연결
- `java-backend`: 파일 저장과 관리 규칙
- `test`, `validation`: 기능·화면 검사
- `docs/assignment`: 설계·관계도·실행·검증 자료

“화면의 기존 요청 주소를 유지했습니다. 사용자가 저장을 누르면 Node 서버가 Java 프로세스에 JSON을 보내고, Java가 저장한 결과를 JSON으로 돌려줍니다.”

## Java 설명: 약 2분

[클래스 관계도](ARCHITECTURE.md)를 보여줍니다.

1. **Main**은 요청을 담당 클래스에 보냅니다.
2. **JobRepository**는 제목·메모·사진과 순서를 저장합니다.
3. **SnapshotService**는 입력 해시로 버전 폴더를 만들고, 같은 입력이면 재사용합니다.
4. **DraftRepository**는 이전 편집본을 이력에 남기고 초안을 저장합니다.
5. **StorageService**는 용량을 계산하고 해당 글만 삭제합니다.
6. **CategoryService / PromptService / StyleService**는 분류와 글쓰기 지침을 관리합니다.
7. **Workspace / JsonFiles / AppException**은 경로·파일·오류를 공통으로 처리합니다.

“클래스마다 책임을 나누고 반복되는 파일 작업을 묶었습니다. 억지로 상속 구조를 만들지 않았습니다. 저장 전에 경로와 사진 해시를 검사합니다. 다른 창이 지침을 바꾸면 revision 값이 달라지므로 충돌을 안내합니다.”

## 인터넷 없이 시연

의존성 설치와 Java 빌드는 미리 해 둡니다. 시연용 자료 폴더를 따로 사용합니다.

```powershell
$env:HDEV_JAVA_DATA_DIR = 'C:\JavaBlogData\presentation'
npm.cmd run desktop
```

1. 첫 실행의 티스토리 연결 창을 닫고, 새 글을 만들어 테스트 캡처 한 장을 넣습니다.
2. 제목·메모를 적고 **직접 작성하기**를 누릅니다.
3. 문단·코드·표를 넣어 미리보기를 확인합니다.
4. **초안 보관** 후 보관함에서 다시 엽니다. 재시작해도 남는 것을 보여줍니다.
5. **내 말투**에서 기본 지침과 **카테고리 없음**의 별도 지침을 저장합니다. 오프라인에서는 기본 분류를 사용합니다.
6. 자료 폴더의 `draft.json`, `history`, `style/category-prompts.json`을 보여줍니다.
7. 시연용 글만 삭제하고 다른 글이 남는지 확인합니다.

Java 실제 연결 증거로 웹 실행의 `/api/java` 응답, `java-store.mjs`의 프로세스 실행 코드, 통합 검사의 “Java가 없으면 저장하지 않음” 항목을 보여줍니다.

## 계정 연결과 최신 버전 설명

“티스토리에 로그인하면 계정이 운영하는 블로그를 찾고, 선택한 블로그의 이름을 화면에 보여줍니다. 이 로그인 화면은 Electron이 읽습니다. 분류 목록과 글쓰기 지침은 선택한 블로그에 맞춰 Java에서 불러옵니다. 이전 글과 사진, 기본 지침은 그대로 둡니다. 카테고리는 글 관리에서 읽기 때문에 새 글 편집기나 복구된 초안을 건드리지 않습니다.”

계정 없이 설명할 때는 `npm.cmd run test:account`로 만든 `.runtime/account-qa/connected.png`를 보여줄 수 있습니다. 이 화면은 모의 계정 검사 자료입니다.

v0.7.4는 이 화면과 기능을 유지하고, 자동 화면 검사가 완료된 뒤 남아 있는 HTTP 연결 때문에 종료되지 않던 문제를 수정한 버전입니다. Java 클래스와 자료 형식은 그대로입니다.

## 예상 질문

**왜 전부 Java로 바꾸지 않았나요?**

기존 화면과 AI·티스토리 기능을 보존하는 요구에 맞췄습니다. 저장과 관리처럼 책임을 나누기 좋은 부분을 Java로 옮겼습니다.

**Java는 단순 파일 쓰기만 하나요?**

글 ID·경로 검사, 사진 해시, 입력 버전과 재사용, 편집 이력, 카테고리 정합성, 지침 충돌 검사와 선택, 용량·전체 삭제 규칙도 처리합니다. 화면용 블록 검증과 발행 규칙은 기존 JS에 남깁니다.

**DB는 왜 사용하지 않았나요?**

기존 JSON·사진 폴더와 호환되어야 하므로 파일 저장을 유지했습니다. DB 변환 없이 자료를 복사해 사용할 수 있습니다.

**직접 작성한 클래스 수는?**

11개입니다. 빌드 스크립트가 30개 제한을 확인합니다. Gson은 외부 JSON 라이브러리입니다.

**원본 자료가 바뀌지 않나요?**

별도 소스 폴더와 앱 식별자·자료 폴더를 사용하고 원격 Git 연결도 제거했습니다. 기존 자료를 가져올 때도 복사본을 사용합니다.

**모든 기능을 실제 서비스에서 시험했나요?**

로컬 기능, 실제 Java 연결, Electron 화면과 모의 발행을 검사했습니다. 실제 AI 품질·로그인·공개 발행 성공은 별도 확인이 필요합니다. 자동 검사 때문에 실제 글을 게시하지 않았습니다.

**개선할 점은?**

요청마다 JVM을 시작하는 비용이 있습니다. 규모가 커지면 Java 상주 프로세스와 비동기 통신을 검토할 수 있습니다. 현재 JSON 교체는 파일 하나 단위이며 여러 파일을 하나의 DB 트랜잭션으로 묶지는 않습니다.
